# Схемы процессов: нотация и формат спецификации

Читай этот файл, когда пора рисовать схему «как есть» или схему варианта. Схема строится из спецификации JSON скриптом `scripts/draw_process.py` из папки навыка; в спецификации нет координат, только дорожки, колонки и связи, раскладку считает скрипт. Образец спецификации выводит ключ `--example`; полный пример с тремя схемами одного процесса («как есть», умеренный и смелый варианты) — `examples/obsledovanie_supd_shemy.json`, пример со всеми видами блоков — `examples/mini_dogovor.json`. Скрипт и примеры ищи по абсолютному пути папки навыка (как его найти — SKILL.md, раздел «Схемы», и `references/platforms.md`).

## Нотация

Нотация — упрощённый BPMN: дорожки, блоки действий, события, развилка, стрелки хода работы и передачи сведений. Лишнего из BPMN нет намеренно: схема должна читаться руководителем без подготовки.

| Элемент | Как выглядит | Когда применять |
|---|---|---|
| Дорожка (`lanes`) | горизонтальная полоса с подписью слева | роль или орган: органы решения, подразделения, внешние стороны, агенты (всегда одна дорожка; если в процессе есть шаги правил или обычной автоматизации, назови её «Агенты и правила» или дай системе свою дорожку), исполнитель; лучше дорожка на роль, всего не больше семи (скрипт проверяет); у всех схем одного процесса id, подписи и порядок дорожек одинаковы |
| Этап (`phases`) | подпись над колонкой; этап на несколько колонок — со скобкой; под подписью охристый ритм этапа (`note`: «раз в квартал», «сентябрь и март») | колонки схемы; ход времени слева направо; ритм показывает, чего этап ждёт |
| `human` | белый блок, серая рамка | действие человека |
| `agent` | бирюзовый блок | действие ИИ-агента; разовый вызов модели без выбора пути рисуй тем же видом и пиши в тексте блока «вызов модели» |
| `rule` | серо-голубой блок | шаг, который выполняет правило, справочник или обычная автоматизация (расчёт по минимуму и максимуму, сверка по реестру, напоминание по сроку) |
| `wait` | охристый блок, пунктир; поле `note` — что именно теряется | ожидание, дозапросы, итерации правок, очередь |
| `call` | белый блок, точечная рамка | человек включается по вызову агента или владельца |
| `decision` | белый блок, жирная рамка | решение человека, которое нельзя отдать агенту |
| `gateway` | ромб с вопросом | развилка хода работы; ответы пишутся подписями стрелок («да», «нет») |
| `option` | бирюзовый блок, пунктир | модуль по согласию владельца, необязательная часть |
| `start`, `end` | круг с подписью под ним | начало и конец процесса, если они нужны для чтения |
| `result` | тёмный блок справа с перечнем составляющих результата | паспорт результата; одинаков на всех схемах процесса |

Стрелки (`edges`): `flow` — ход работы (серая сплошная); `message` — передача сведений между дорожками (серая штриховая); `option` — связь по согласию (бирюзовая штриховая); `call` — вызов человека (чёрная точечная); `wait` — ожидание и итерации (охристая); `decision` — передача результата или решение (чёрная толстая). Поле `both: true` рисует наконечники с обеих сторон. Стрелка в `result` идёт от последнего шага процесса, обычно приёмки или подписи; кто отвечает за результат, пишет подвал блока результата (`footer`).

## Формат спецификации

Файл содержит один объект или список объектов; список даёт несколько схем на одной HTML-странице («как есть» и варианты). Все тексты — по-русски, с буквой ё; перенос строки внутри блока — символ «|», без него скрипт переносит по словам сам.

```json
{
  "page_title": "Название страницы (только у первой схемы списка)",
  "eyebrow": "Вариант 1 из 3",
  "title": "Как есть",
  "subtitle": "Одна фраза о сути варианта",
  "caption": "Подпись под схемой на странице",
  "lanes": [
    {"id": "z", "label": "Заказчик"},
    {"id": "a", "label": "ИИ-агенты", "note": "агентов нет"},
    {"id": "m", "label": "Методолог"}
  ],
  "phases": ["Документы", {"label": "Сбор параллельно", "span": 2, "note": "в темпе Заказчика"}, "Отчёт"],
  "nodes": [
    {"id": "z1", "lane": "z", "col": 0, "row": 0, "span": 1, "kind": "wait",
     "title": "Собирает документы", "text": "по подразделениям", "tag": "почта", "note": "ожидание, дозапросы"}
  ],
  "edges": [
    {"from": "z1", "to": "m1", "kind": "flow", "label": "документы", "both": false, "route": "auto"}
  ],
  "result": {"title": "Результат", "heading": "Одинаков во всех вариантах",
             "items": ["Отчёт", "Дорожная карта"], "footer": "Отвечает Исполнитель"},
  "metrics": ["Срок до акта: 8–10 недель", "Трудозатраты людей: 45–55 человеко-дней", "Заказчик видит выводы: в конце", "оценка"],
  "legend": true
}
```

Поле схемы `columns` задаёт число колонок, если нужно больше, чем дают этапы и блоки (например, чтобы вариант стоял на той же сетке, что «как есть»).

Поля блока: `id` (латиницей, уникален), `lane`, `col` (целое с нуля), `row` (целое, ряд внутри дорожки, с нуля), `span` (целое не меньше 1, ширина в колонках), `kind`, `title`, `text`, `tag` (мелкая серая подпись: инструмент, платформа или номера шагов «как есть», которые блок закрывает, — «ш. 7, 12»), `note` (охристая подпись: что теряется). Поля стрелки: `from`, `to` (id блока или `result`), `kind`, `label`, `both`, `route` — `auto`, `v` (вертикаль), `h` (горизонталь), `hvh` (в зазор между колонками, вертикаль, в блок), `vh` (вниз или вверх, затем вбок), `hv` (вбок, затем вниз или вверх); `dx`, `dy` сдвигают подпись, если она легла на линию. Заметка `note` у дорожки показывается под её подписью, только если дорожка пуста.

## Правила раскладки

1. Колонки — этапы процесса во времени. Передача между дорожками остаётся в той же колонке: блок-получатель стоит прямо под или над отправителем, стрелка вертикальная. В следующую колонку переходи, когда следующий шаг идёт после по времени.
2. Не больше восьми колонок, семи дорожек и двадцати четырёх блоков на схеме; скрипт считает превышение нарушением правила. Длинный процесс дели на две схемы по этапам или объединяй соседние шаги в один блок («Сбор и разбор»).
3. Один шаг — один блок: заголовок до трёх слов, текст до трёх коротких строк. Подробности уходят в документ, схема отвечает на вопрос, где лежит работа.
4. Ряды (`row`) внутри дорожки — для параллельных действий одного участника в одной колонке и для модулей по согласию под основным блоком.
5. Блок шириной в несколько колонок (`span`) закрывает зазоры между ними, и стрелки между соседними дорожками не смогут его обойти. В дорожке, которую пересекают стрелки, растягивай блок только там, где через него ничего не идёт, иначе дели его на блоки по колонкам.
6. Точки ожидания отмечай блоком `wait` с заметкой, что теряется и какое это ожидание: сведений, обязательного контроля или физического исполнения. На схеме варианта ожидание сведений обычно исчезает, а обязательный контроль и физическое время остаются и названы. На схеме варианта видны нормальный ход, существенные исключения (развилка или блок «по вызову») и точки, где решает человек.
7. Блок результата и строка показателей (`metrics`) одинаковы по составу на всех схемах одного процесса: те же подписи до двоеточия в том же порядке, меняются только значения. Показатели подбирай под процесс, обычно три–четыре: срок или такт процесса; «Трудозатраты людей» — суммарно по всем ролям, обязательно (отчёт без этой строки на схеме «как есть» не собирается); при необходимости трудозатраты роли, чьё время задаёт ход процесса («Трудозатраты методолога»); показатель результата из паспорта — для разового процесса момент, когда главный потребитель видит результат или его черновик («Заказчик видит концепцию: в первый день»), для повторяющегося — качество результата («Ходовой товар на полке: …») или доля доработок. Значение пиши числом или диапазоном с единицей, у одного показателя на всех схемах единица одна: «45–55 человеко-дней» и «13–18 человеко-дней», а не человеко-дни на одной схеме и человеко-часы на другой; иначе изменение не посчитается. Если значения — гипотезы, последним элементом поставь слово «оценка» без двоеточия: скрипт нарисует его плашкой. Пометка без двоеточия показателем не считается и скриптом не сверяется, поэтому на схеме с замеренными значениями её можно не ставить.
8. Все схемы одного процесса — в одном файле списком: скрипт проверит, что дорожки (id, подписи, порядок), состав результата, ответственный в подвале и подписи показателей совпадают, а расхождение считает нарушением правила, и нарисует все схемы на странице в одном масштабе, поэтому вариант со слитыми этапами выглядит уже, а не крупнее. Опорный вариант «помощники», если ему всё же нужна схема, держи на тех же этапах, что «как есть»: так видно, что структура не изменилась. На схеме смелого варианта люди остаются в блоках решения, приёмки, доверительной беседы и вызова (`decision`, `call`), основная работа — в дорожке агентов.

## Запуск

Запускай по абсолютному пути и пиши результаты в отдельную папку: рабочая папка агента часто не совпадает с папкой навыка, и относительный путь `scripts/draw_process.py` тогда не находится.

```
python3 "<папка навыка>/scripts/draw_process.py" "<папка результатов>/Схемы_процесса_<имя>_v1.0.json" \
        -o "<папка результатов>/Схемы_процесса_<имя>_v1.0" --strict --mermaid
```

Скрипт пишет SVG на каждую схему, одну HTML-страницу со всеми схемами в одном масштабе, по ключу `--mermaid` — текст Mermaid на каждую схему (`.mmd`), по ключу `--png` — PNG, только если установлен пакет cairosvg (без него скрипт пропускает PNG и сообщает об этом; листам, отчёту и проверке PNG не нужен: схему смотри в HTML или SVG). Ключ `--check` проверяет всё, не записывая файлов. Листы согласования и итоговый отчёт со встроенными схемами собирает тот же скрипт в режиме `--report` (`references/report-spec.md`); номер схемы в них — её порядок в файле схем. Сообщения по-русски трёх видов:

- «ошибка» — схема не нарисована: неверный JSON, поле не того типа (`col` строкой, `span` меньше 1), пустой список схем, стрелка к несуществующему блоку, занятая ячейка;
- «нарушение правила» — схема нарисована, но нарушена нотация: неизвестный вид блока или стрелки, превышены пределы колонок, дорожек или блоков, схемы одного процесса разошлись по дорожкам, результату, ответственному или подписям показателей, в тексте или показателе слово «труд» вместо «трудозатраты»;
- «замечание раскладки» — стрелка проходит через блок, две стрелки слились в одну линию, подпись задевает блок или другую подпись, текст шире блока.

Код возврата 0 — готово; 1 — есть ошибки, а с ключом `--strict` ещё и нарушения правил или замечания раскладки; 2 — неверный вызов. Слившиеся стрелки скрипт сначала разводит сам, сдвигая общий участок одной из них; общий ствол стрелок одного вида из одного блока или в один блок замечанием не считается.

Как исправлять: стрелку через блок — переставь блоки так, чтобы получатель стоял в той же колонке, раздели растянутый блок или задай `route`; подпись — сократи, сдвинь полями `dx`, `dy` или убери, если стрелка понятна без неё; длинную строку — сократи или разбей символом «|». После двух неудачных исправлений одной схемы упрости её: объедини соседние шаги, убери второстепенные стрелки, вынеси подробности в текст. Ноль нарушений и замечаний — обязательный минимум, но скрипт не судит, понятна ли схема: если среда показывает картинки, посмотри на каждую схему и проверь, нет ли стрелки, которую можно прочитать не туда.

## Что показать человеку

Владелец видит схемы на листах согласования и в итоговом отчёте: там они в одном масштабе, с вкладками и кнопкой «Открыть крупно». Картинки схем в переписку не отправляй. Отдельный файл схем нужен для перерисовки и прикладывается по просьбе. Если страницы собрать нельзя, по порядку, что доступно в канале: текст Mermaid, если канал его показывает (Mermaid не передаёт колонки этапов, поэтому скрипт пишет этап в начале подписи блока); таблица «дорожка × этап» с короткими пояснениями. Если показан запасной вид, скажи об этом одной фразой. JSON человеку не показывай.

## Если скрипт запустить нельзя

Без Python напиши Mermaid сам по тому же устройству: дорожки — подграфы, блоки — узлы, вид блока — класс с цветом, стрелки — по виду. Служебные слова Mermaid (`end`, `call`, `click`, `style`, `class`) не используй как имена узлов и классов, кавычки внутри подписей заменяй на «ёлочки».

```
flowchart LR
  subgraph L1["Заказчик"]
    z1["[Документы]<br/>Собирает документы<br/>ожидание, дозапросы"]
  end
  subgraph L3["Методолог"]
    m1["[Документы]<br/>Анализ документов"]
  end
  z1 -->|"документы"| m1
  res(["Результат<br/>• Отчёт<br/>• Дорожная карта"])
  m1 ==> res
  classDef v_wait fill:#FAEBD2,stroke:#9C5F0E,stroke-dasharray:5 3
  class z1 v_wait
```

Если канал не показывает и Mermaid, дай таблицу «дорожка × этап»: строки — дорожки, столбцы — этапы, в ячейке — блок с пометкой вида в скобках, стрелки — словами под таблицей. Спецификацию JSON всё равно приложи файлом: её нарисует любой, у кого есть Python.

| | Документы | Интервью и анкета | Синтез и отчёт | Замечания |
|---|---|---|---|---|
| Заказчик | Собирает документы (ожидание) | Интервью и анкета (ожидание) | | Замечания к отчёту (итерации) |
| ИИ-агенты | | | | |
| Методолог | Анализ документов | Интервью, протоколы | Синтез, отчёт | Доработка → результат |
